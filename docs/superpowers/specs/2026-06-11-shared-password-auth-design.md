# Shared-Password Auth + Deploy Tooling for Cloud Deployment — Design

**Date:** 2026-06-11
**Status:** Approved (revised — deploy tooling expanded per Danilo's constraints)

## Problem

The cloud (Cloud Run + GCS) deployment has no built-in authentication, and
deploying it is a long copy-paste sequence in `docs/deploy-cloud-run.md`. The
current auth options are the gcloud IAM proxy (requires `gcloud` on every
client machine) or a fully public URL (exposes a ~$0.70/hr GPU and every
session in the bucket to anyone who finds it).

## Goals

**Auth:** a single shared password — three auto-generated words — that:

1. is generated by the deploy script and shown to the operator,
2. is sent on **all** web requests from the frontend,
3. is validated by the Flask backend on every `/api/*` request,
4. is entered by the user once per browser via a small password screen.

**Deploy tooling** (Danilo's constraints):

1. Deploys to any custom GCP project from scratch — enables APIs, creates the
   registry/buckets/service account, builds and uploads the image, deploys.
2. Idempotent and cheap to re-run — hashes build inputs and probes existing
   resources so nothing is rebuilt or re-uploaded needlessly.
3. Documented for both humans and coding agents (Claude, Codex, Antigravity):
   a user should be able to open an agent, point it at the deploy docs, and
   say "deploy this" — and the agent can also read logs and run tests.
4. Tracks what it created so the user can tear it down from the script
   without opening the Cloud console.
5. Well-commented so a human can inspect it step by step.

Threat model for auth: keep strangers off a paid GPU and out of session data.
Not multi-user, not bank-grade. TLS is provided by Cloud Run.

## Decisions (made during brainstorming)

- **Mechanism: Flask header check + app-level prompt** (chosen over nginx
  basic auth and query-param tokens). The check lives in Flask so it protects
  the API regardless of what sits in front; query params were rejected because
  tokens leak into request logs.
- **Frontend** prompts once and persists the password in `localStorage`.
- **`/api/health` is also protected.** The heartbeat keeps the GPU container
  alive (billed time), so an open health endpoint would let anyone keep the
  service warm. The frontend heartbeat already goes through `api.ts` and can
  send the header.
- **Password is retrievable**, not strictly shown-once: `deploy.sh password`
  reads it back from the live service config. It is visible to project admins
  in the Cloud Run console anyway; pretending it is unrecoverable adds
  friction without security. This also lets agents fetch it for smoke tests.
- **`down` keeps user data by default**: the sessions bucket and model
  weights survive teardown unless `--purge` is passed (with an extra explicit
  confirmation).
- **Agent quick-reference is a plain README** (`deploy/README.md`), not a
  Claude-specific skill file, so it serves any agent. It must be compact
  enough (~1–2k tokens) that an agent with a <100k context window can read it
  and immediately operate the tool.

## Design

### 1. Deploy script — `deploy/deploy.sh` with subcommands

One bash script, organized as numbered step functions, each with a comment
block explaining what it does and why. `python3` one-liners handle JSON
state, hashing, and password generation (python3 is a project prerequisite).

```
./deploy/deploy.sh up          # default — idempotent provision + deploy
./deploy/deploy.sh status      # what exists, service URL, image hash, last deploy
./deploy/deploy.sh logs [-f]   # read/tail Cloud Run logs (wraps gcloud)
./deploy/deploy.sh password    # print the current password (read from service env)
./deploy/deploy.sh smoke       # authenticated curl checks: /api/health, /api/status
./deploy/deploy.sh down        # tear down what the script created
```

**`up` — check-then-act at every step.** Each step probes current state,
skips if already satisfied, and records what it *created* (vs found
pre-existing):

1. **Preflight**: `gcloud` present and authenticated, project set and
   reachable, billing enabled. Clear, actionable error message per failure.
2. **Enable APIs** (`run`, `cloudbuild`, `artifactregistry`, `storage`) —
   only the ones not already enabled.
3. **Artifact Registry repo, service account + bucket IAM, models/sessions
   buckets** — create-if-missing. Names default from the project
   (`${PROJECT}-sam3-sessions`, `${PROJECT}-sam3-models`), overridable via
   env vars/flags. Only `PROJECT` is required; `REGION` defaults to
   `us-central1` (L4-capable).
4. **Model weights**: skip if `gs://<models-bucket>/sam3/` is populated;
   otherwise download via `hf` (requires a HuggingFace token for the gated
   model — the one genuinely manual prerequisite, called out loudly) and
   upload once. Never re-pushes the ~7 GB.
5. **Build, cached by content hash**: hash the build inputs (`backend/`,
   `frontend/`, `Dockerfile.native`, deploy configs) → image tag
   `sam3-native:<hash>`. If that tag already exists in the registry, skip
   Cloud Build entirely. A code change produces a new hash → rebuild, which
   itself reuses heavy layers via the existing `--cache-from` setup.
6. **Deploy**: if the service already runs this exact image hash with
   unchanged configuration → "already up to date", no deploy. The password is
   **reused from the live service's `AUTH_PASSWORD`** on redeploys; a fresh
   one is generated only on first deploy or with `--rotate-password`
   (`secrets.choice` over an embedded list of ~256 short common words →
   `crimson-otter-lantern` style, ~24 bits of entropy). Deploys with
   `--allow-unauthenticated` — the password replaces IAM as the gate — and
   the existing flags from `docs/deploy-cloud-run.md` (L4 GPU,
   max-instances 1, concurrency 8, etc.).
7. **Report**: print URL + password + pointer to the smoke tests.

**State file**: `deploy/.deploy-state.json` (gitignored) — project, region,
resource names, a `created_by_script` flag per resource, deployed image hash,
timestamps. `down` deletes **only** resources the script created, in reverse
order, with a TTY-guarded confirmation; sessions bucket and weights are kept
unless `--purge`.

**Non-interactive safe**: every prompt is TTY-guarded per the repo
deploy-script convention (non-interactive stdin auto-proceeds with a log
line; never a silent `exit 0`); `--yes` opts into auto-confirm so agents can
run it.

### 2. Backend — `app/config.py` + `app/__init__.py`

- `app/config.py` reads `AUTH_PASSWORD` from env (`None` when unset).
- A `before_request` hook in `create_app()`: if `AUTH_PASSWORD` is set, every
  request — including `/api/health` — must carry a matching `X-Auth-Token`
  header, compared with `hmac.compare_digest`. Missing or wrong →
  `401 {"error": "unauthorized"}`.
- When `AUTH_PASSWORD` is unset (local dev, tests), the hook is a no-op —
  zero behavior change locally.
- The `/api/health` route comment ("no auth") is updated, since it is no
  longer true when `AUTH_PASSWORD` is set.

### 3. Frontend — `api.ts` interception + `PasswordGate`

- `api.ts` gains:
  - a module-level token initialized from `localStorage["sam3-auth-token"]`,
  - a `setAuthToken(token)` export that updates the module state and
    localStorage,
  - an `onUnauthorized(callback)` registration,
  - an `apiFetch(url, init)` wrapper that injects `X-Auth-Token` and invokes
    the callback on any 401 response.
- All `fetch(` calls inside `api.ts` switch to `apiFetch(`. The XHR upload
  adds one `xhr.setRequestHeader("X-Auth-Token", ...)` after `open()`.
- `App.tsx` registers the callback → sets an `authRequired` state → renders a
  `PasswordGate` component (centered card, password input + submit, shadcn
  styling). Submit validates the candidate against `/api/health`; success
  saves the token via `setAuthToken` and clears `authRequired`; failure shows
  an inline error and stays on the gate.
- Local dev: the backend never returns 401, so the gate never appears.

### 4. Docs

Three layers, smallest first:

- **`deploy/README.md` — agent quick-reference (~1–2k tokens, self-contained).**
  The canonical entry point for a short-context agent: subcommand table,
  exact commands to get the URL / password / logs, an authenticated `curl`
  smoke-test example with `X-Auth-Token`, the state-file location, and a
  short common-errors → fixes table. No narrative; a link to `DEPLOY.md` for
  everything else.
- **`DEPLOY.md` at the repo root — full reference for humans and agents.**
  Quickstart (prerequisites: gcloud auth, billing, HF token → then
  `./deploy/deploy.sh up`), an agent runbook (command-per-task table:
  deploy, read logs, get password, run smoke tests, check status, tear
  down), how the idempotency/hash-skip keeps re-runs free, and the cost
  table, GPU rationale, and troubleshooting carried over from
  `docs/deploy-cloud-run.md`.
- **`docs/deploy-cloud-run.md`** becomes a thin pointer to `DEPLOY.md` so no
  two divergent copies exist.

`USER-FLOWS.md` is amended in the same commit as the auth change — new
auth-gate flow, plus a note that all API requests carry `X-Auth-Token` in
cloud mode (per the harness rule in CLAUDE.md).

### 5. Testing

- Backend pytest, with `AUTH_PASSWORD` set: missing header → 401, wrong
  header → 401, correct header → 200; with it unset: everything open.
  `/api/health` is included in the matrix.
- Frontend: `npx tsc --noEmit` and the production check `tsc -b && vite
  build`; manual gate verification via `make dev` with `AUTH_PASSWORD` set
  locally.
- Deploy script: `bash -n` syntax check; the pure helpers (input hashing,
  password generation, state-file read/write) are factored so they can be
  exercised without GCP. The gcloud-touching paths are verified by a real
  deploy run (`up` twice — second run must be all-skip — then `smoke`, then
  `down`), since no emulator exists for them.

## Out of scope

Rate limiting, multiple users / per-user passwords, session expiry,
protecting the static HTML/JS (the app is open source; only the API needs
the gate), Terraform/IaC (the script with a state file is deliberately
simpler), and CI-driven deploys.
